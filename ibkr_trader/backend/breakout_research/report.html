Breakout Signal Quality

breakout_scanner.py sends ~28 alerts/day (range 10–51) at a 52.9% win rate and +0.05% average return — essentially noise. This is a running log of real, backtested candidate filters to fix that, including the ones that didn't hold up.

The headline finding

Validated on 3 independent real datasets · not yet live

Exclude PRE-BREAKOUT alerts with %B 75–85, and RSI ≥80

PRE-BREAKOUT is 89% of all simulated alert volume and consistently the weaker signal type. Within it, %B turns out to be non-monotonic — the 75–85 band is a real "dead zone," worse than either the 65–75 or 85–95 bands flanking it. Excluding that dead zone, plus dropping RSI≥80 entries, was tested three ways:

Methodology

Three real, escalating rigor levels: (1) mined the 8 fields breakout_scanner already captures per alert against the real 2-month live population (1,107 alerts); (2) built a naive 5-year "raw Bollinger transition" proxy across the full 112-ticker universe to test genuinely new features — found this proxy gives misleading answers once cross-checked against real live outcomes, because it ignores the scanner's own F2/F5/F6/F7/F8/F9/F10 gates; (3) extended the account's own already-validated intraday-faithful simulation (real Alpaca minute bars, exact gate replication, today's real production settings) across 2.5 years / 86 tickers — 1,420 properly-gated alerts — then cross-validated every candidate finding directly against the real live alert stream before trusting it.

BREAKOUT-type alerts: no filter needed

Tested the same features against BREAKOUT alerts specifically (n=150). Smaller sample, more mixed picture — real leads (ADX<30 beats ADX≥30 at 55–57% vs 45–49% win rate; a non-monotonic confirmation-time pattern) but none as clean as the PRE-BREAKOUT finding, and not yet cross-validated against live data. Conclusion: BREAKOUT doesn't need aggressive filtering — it's already a smaller share of volume (~11%) and a meaningfully better performer on its own (avg +1.75–1.83% vs PRE-BREAKOUT's +0.34–0.51%). Flagging the ADX lead as a real thread, not a validated result.

Ranking within PREFER: most to least promising

A smooth numeric score was tried first and rejected — with these features and this sample size it produced only 16 distinct values, one bucket driven to a −7% average by just 13 outlier alerts. A 3-level ranking is what the data actually supports, and it's clean: monotonic on both the 3-day and 5-day horizon.

Honest finding, not smoothed over: PREFER-LOW is actually negative — worse than NEUTRAL, despite clearing the coarse PREFER bar. The boundary from the first pass was a bit loose at the edges; rather than quietly re-drawing it, PREFER-LOW is now its own visible tag. HIGH is built from real, validated components: for BREAKOUT, ADX<30; for PRE-BREAKOUT (already near the 52-week high), clearing ≥2 of 3 checks — %B in the 65–75 sweet spot, within 2% of the 52-week high, and volume confirmation ≥1.5×.

Now running: live out-of-sample validation

shadow_filter_monitor.py tags every new live alert with the full 5-level tier (AVOID / NEUTRAL / PREFER-LOW / PREFER-MID / PREFER-HIGH) in real time — read-only against breakout_scanner's real alert table, no Telegram, nothing wired to anything live. One real engineering wrinkle handled honestly: ADX and distance-from-52-week-high aren't columns the live scanner captures, so the monitor computes both itself from a real intraday price pull per ticker at tagging time. A retroactive test run against all 1,168 historical alerts confirmed the code executes correctly, but also surfaced a real limitation worth stating plainly: that retroactive run used today's price data for old alerts rather than each alert's own historical date, so it isn't a valid backtest — only a plumbing check. Going forward, real-time computation is exactly correct, since "today's data" is the right timeframe for a live alert. Log is running clean from here.
